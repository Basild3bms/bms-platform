# M2.1F Flutter foundation plan

1. Audit the M1 mobile shell, API contract, Flutter SDK, and local toolchains. Generate Android and iOS runners without replacing application source. Configure identifiers, minimum platform versions, ignored artifacts, and mobile CI.
2. Add a modular application shell with Riverpod preferences, Dio status client, GoRouter sections, secure token storage boundary, localized English/French labels, themes, and a reusable unavailable state. Keep every dashboard section free of simulated building values.
3. Validate dependency resolution, static analysis, unit/widget tests, and the existing API regression suite. Build Android only where an SDK is available. Document setup, architecture, limitations, and release blockers.
4. Review this foundation before implementing login, bearer token attachment, organization selection, or authenticated navigation.

The next phase will use the exact authentication endpoints and response shapes in `packages/contracts/openapi.yaml`. It needs tests for token expiry, disabled accounts, failed login, logout revocation, unauthorized requests, and tenant selection before shipping an authenticated screen. Stage 1 resolved the organization discovery contract gap with `GET /api/v1/auth/organizations`; the mobile login and selection UI remains unimplemented.

## Proposed next stage: mobile authentication and organization selection

This is a plan only. The Windows Android 17/API 37 debug run of commit `54413b0` validated the overview and public status request on `emulator-5554`; it did not exercise authentication or tenant data.

1. **Contract and state tests first.** Add tests for the existing Laravel/OpenAPI shapes: `POST /api/v1/auth/login` sends `email` and `password` and returns `token`, `token_type: Bearer`, `expires_at`, and a minimal `user`; 401 is a generic credential or inactive-account failure, 422 is invalid input, and 429 is the login limit. `GET /api/v1/auth/me` returns the user or 401. `GET /api/v1/auth/organizations` returns `data` entries with only `id`, `name`, `role`, and server-derived `permissions`, or 401. `POST /api/v1/auth/logout` returns 200 on revocation or 401 for an invalid session. Test malformed responses, transport failure, secure storage failure, and no token exposure in logs.
2. **Session boundary.** Add typed response models, an auth client, and a Riverpod session controller around the existing `TokenStore`. Keep the token and its expiry in secure storage; never persist passwords. Attach `Authorization: Bearer` only to protected requests, leaving status and login public. On cold start, read the token, reject a locally expired token, and confirm a remaining token with `/auth/me` before opening protected navigation. Treat the server's 401 as authoritative: clear token, selected organization, and in-memory protected data. On network failure, retain the token for retry but keep protected screens closed. Fail closed if secure storage cannot be read. Assign each session a generation ID; cancel pending requests and check the ID after every asynchronous boundary before writing storage, changing navigation, or publishing data. A late login or restore response must never reactivate a session after logout.
3. **Login and navigation.** Add localized English/French login, loading, validation, rate-limit, and retry states. Change the current `/:section` router to explicit public login, startup, organization selection, and protected shell routes. Route guards must wait for session restoration and must not flash the shell before validation. A successful login stores the token and expiry, validates the response, then fetches current organizations; an empty list shows an access-free state rather than selecting a tenant.
4. **Organization selection and switching.** Present only entries from `/auth/organizations`; hold the selected organization ID in session state and revalidate it against a fresh discovery response on restoration. Selection conveys context to later tenant-scoped routes but is never an authorization claim. Switching organizations must cancel pending scoped requests, advance the session/organization generation, and clear any former organization's in-memory data before navigation. Accept a response only when its token and organization ID still match the active context. If a future scoped request returns 403 or 404, clear the selection and any scoped data, refresh discovery, and show an access-changed state. Do not add building-data calls or cached tenant data in this stage.
5. **Logout and failures.** Call `/auth/logout` with the current bearer token. On 200 or a definitive 401, clear local token, expiry, selected organization, and protected state, then navigate to login. On transport or server failure, show that remote revocation is unconfirmed and offer retry; if a local-only sign-out is provided, label it explicitly because the server token may remain valid until its 12-hour expiry. Never report logout success merely because local storage was cleared.
6. **Acceptance gates.** Before implementation, write unit and widget tests for login 200/401/422/429, expiry and revocation, disabled accounts, token write/read/delete, startup network uncertainty, route guards, empty/multiple memberships, switching, lost organization access, and logout failure paths. Use controlled delayed responses to prove that logout, token revocation, and organization switching invalidate earlier asynchronous work, including storage writes and cached or displayed tenant data. Test English/French text and light/dark screens. Then run Flutter analysis and tests, backend SQLite and isolated PostgreSQL tests, and Android debug build. Validate login, restoration, selection, switching, access loss, and logout on the Windows emulator without printing credentials or tokens. Keep physical writes disabled and leave release signing and production access outside this stage.
