# Security baseline

M2.2C.3 Flutter Floors and Zones use only protected bearer GET requests. Response parsers require exact organization and parent identifiers, detail IDs, signed integer levels, contracted zone types, and valid pagination. Controllers cancel and discard requests on parent navigation, organization changes, screen exit, and logout; the router guards unauthenticated hierarchy deep links. Laravel remains the authorization authority. This client-side work does not resolve the secure-storage combined-failure commercial-release blocker.

The final Flutter source audit added UUID-shape validation at the Floor and Zone API boundary, duplicate resource rejection within and across pages, and provider mount checks before processing late asynchronous replies. These client checks fail safely and do not authorize access; server-side membership and parent-scoped queries remain required. The secure-storage release blocker remains open.

`GET /api/v1/auth/organizations` uses the existing Sanctum bearer and active-user checks. It returns only the authenticated user's active memberships, minimal organization identity, and roles and permissions read from the server's current role mapping. It does not accept client-supplied authorization claims, expose membership IDs or user lists, or reveal foreign organizations. M2.1 has no organization active/status field, so membership activity is the available status gate. Clients must still use tenant-scoped server authorization for every later data operation.

The Stage 2 mobile API configuration accepts local HTTP only in development, with a debug Android network rule limited to emulator and loopback hosts. Release configuration requires an explicit HTTPS origin, and its Android network security policy explicitly denies cleartext traffic, including Android 17's implicit localhost exception. The public status check exposes only process responsiveness. The Windows Android 17 emulator reached that public route on 2026-11-18. Subsequent Windows validation of M2.2B commit `66fcbbe` confirmed authenticated Buildings list and detail against local PostgreSQL data, plus protected logout/back/reopen behavior; independent server-side token revocation remains unverified.

A direct unauthenticated request without a JSON `Accept` header exposed a missing Laravel login redirect route and returned 500. The API authentication redirect now resolves to no path for `api/*`; the existing JSON exception policy returns 401. Regression tests cover both discovery and the existing `/auth/me` route, and a local HTTP request confirmed `{"message":"Unauthenticated."}` with status 401.

M1 exposes only a status endpoint. Device writes are disabled by default in edge configuration and no protocol adapter or command endpoint is present. Development Compose binds web and API ports to localhost. Example passwords are development placeholders and must be replaced before any shared deployment.

M2.1 uses 12-hour Sanctum bearer tokens, password hashing, generic login failures, five failed attempts per email/IP and twenty failed attempts per IP per minute, organization-scoped membership authorization, and audit records for login and membership changes. An inactive user cannot log in or use an existing token. M2.1 API routes reject web session identities; cookie-based SPA authentication is not yet configured. Token values and passwords are not logged. User invitation requests return the same HTTP 202 shape for new and existing email addresses. The one-time token is stored as a hash, expires in 24 hours, and must be delivered securely to the invitee; the accept endpoint is limited to five requests per minute per client IP. Existing accounts must provide their current password. Invitation tokens are returned to the requesting administrator only for local development; authenticated email delivery, recipient verification, MFA, and refresh/session lifecycle are required before shared deployment. Database triggers reject audit updates and deletes. Database constraints or triggers reject device/building tenant mismatches. Equipment writes remain disabled.

M2.2A building reads require `buildings.view` for active viewer, operator, admin, or owner memberships; creates and updates require `buildings.manage` for active admin or owner memberships. Outsiders and inactive members receive 404 for organization access; active members without permission receive 403. Detail and update resolve building UUIDs under the authorized organization, and `organization_id` in input is rejected. Successful mutations append organization- and actor-scoped audit rows in the same transaction. No delete route is present, so existing device cascade behavior cannot be invoked through this API. These routes do not contact gateways or change equipment state.

M2.2C floor and zone reads require `floors.view` or `zones.view`; writes require the corresponding `.manage` permission. Viewer and operator receive view; admin and owner receive view and manage. A route checks active membership before resolving nested records. Every building, floor, and zone is queried under the authorized URL hierarchy; foreign and mismatched records return 404. Mutation bodies cannot supply organization or parent IDs. PostgreSQL composite foreign keys, SQLite triggers, immutable parent guards, and restrictive delete foreign keys protect the hierarchy even if a future caller bypasses the API. Unique indexes close the validation race for codes, with recognized conflicts returned as 422. Mutations and append-only audit rows share a transaction; an audit failure rolls back the data change. No DELETE or equipment command route was added.

Final M2.2C hardening constrains every new path UUID before PostgreSQL lookup, so malformed identifiers return 404. Organization and parent keys are rejected even when null or empty. Duplicate-code translation checks the database unique-violation code and the specific floor/zone code constraint, so unrelated database failures are not mislabeled as validation errors. Local HTTP validation of the existing owner account and demo building reported logout HTTP 200 followed by HTTP 401 when the same bearer token was replayed against a protected endpoint. Read-only PostgreSQL checks independently confirmed the 3 floors, 6 zones, 12 permission assignments, and all 11 correctly scoped audit rows. The bearer-token replay result does not resolve Flutter secure-storage failure handling; that release blocker remains open.

Related follow-up outside M2.2C scope: the previously merged Buildings routes still lack UUID path constraints, use `prohibited` for `organization_id` (which accepts null/empty), and do not translate a database-level duplicate-code race to 422. They were not changed in this hardening pass.

Stage 3 adds mobile login, bearer requests, secure token/expiry storage, server-validated restoration, organization selection, and local logout. Public status and login requests carry no bearer. Protected navigation stays closed until `/auth/me` and organization discovery succeed; an expired or rejected token is cleared. Network uncertainty offers retry without opening protected screens. Session generations and cancellation prevent late responses from restoring a logged-out session or stale organization context. Organization permissions shown by the app are advisory; Laravel authorizes each later scoped request. Stage 3 contained no building data, control request, or simulated live reading; M2.2B subsequently added read-only building data.

Logout closes local navigation immediately and requests server revocation. Before deleting the secure-storage token, the client overwrites it with a non-token invalidation value. If deletion fails but overwrite succeeds, a restarted app rejects the invalidated record; if overwrite fails but deletion succeeds, the token is gone. Either failure is reported conservatively. Repeated logout retains any warning that server revocation was unconfirmed. If both secure-storage overwrite and deletion fail while server revocation also fails, the old token can remain valid and a new app process may restore it after `/auth/me`; no purely local mechanism can guarantee recovery when all persistent writes and the network are unavailable. This combined failure is an unresolved **commercial-release blocker**. The architecture decision accepts it for development and testing only; it does not approve production release. A robust recovery strategy must be evaluated before commercial distribution. The Android runner disables backup of app data and excludes signing material from Git; release signing and owned application identifiers remain distribution tasks. Development uses loopback HTTP only; shared environments require HTTPS. Authenticated Android Buildings runtime was validated on Windows for commit `66fcbbe`, but independent server-side logout-token revocation verification remains pending. Existing release blockers remain in force.

## Required production controls

Use an identity provider or equivalent MFA-capable login, short-lived sessions, organization memberships and per-action authorization. Enforce tenant scope at query and message boundaries. Authenticate gateways with rotated certificates; encrypt API, MQTT and WebSocket traffic. Store secrets in a secret manager, never source control. Apply network allowlists and segmentation between gateways and building controllers. Commands need two independent checks: cloud policy and edge allowlist, with expiry, bounds and audit trail. Treat telemetry and gateway messages as untrusted input. Review dependencies, sign images, run vulnerability scans and establish incident response, backup encryption and restore drills before production.
