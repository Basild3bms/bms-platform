# M2.2D Flutter Equipment Inventory — Stage 1 design

Status: **proposal for approval; no Flutter implementation in this stage**. Audited on `feature/m2-2d-flutter-equipment` from `1549a83` on 2026-11-20. The current Laravel controller and OpenAPI contract are the implementation source of truth; `M2_2D_EQUIPMENT_ARCHITECTURE.md` records the earlier backend design and contains historical pre-implementation observations.

## 1. Repository audit

- The mobile app is a Riverpod/GoRouter Flutter shell using `material_ui`. `app.dart` supplies light/dark themes and English/French localization through `AppStrings`. `core/network/api_providers.dart` supplies the protected Dio client and bearer interceptor; `TokenStore` persists only auth token, expiry, and selected organization. No equipment client, model, controller, screen, or tests exist yet.
- `features/buildings`, `features/floors`, and `features/zones` already provide read-only GET clients, repositories, typed parsing, list/detail controllers and widgets. Floor/zone clients validate UUID path segments and response ancestry. Their shared `HierarchyPage` verifies pagination and duplicate IDs; `safeHierarchyRead` maps transport/HTTP failures to safe categories. Lists have first page, refresh, load more, empty, retry and offline states.
- `HierarchyController` captures `(userId, organizationId, generation)`, cancels abandoned requests, checks `ref.mounted`, rejects stale completions, and restores a list after canceled pagination. Its `HierarchyScope` carries only building and optional floor, so it cannot distinguish the three equipment list scopes or optional filters. A dedicated equipment scope/controller is preferable to stretching that type or sharing one ambiguous list state.
- `app_router.dart` currently guards the floor/zone hierarchy and sends the drawer's `/equipment` section to an unavailable card. `BuildingDetailScreen` links to Floors, `FloorDetailScreen` to Zones, and `ZoneDetailScreen` has no child link. Route allowlisting must be extended for equipment routes; existing Floors and Zones routes stay intact.
- `SessionController` validates selected membership during restoration, advances a generation on organization changes, and closes protected navigation on logout/401. Equipment state must follow those events. Known mobile secure-storage combined-failure behavior remains a commercial-release blocker; this design does not resolve it.

## 2. Exact read contract

Both operations require a bearer token, an active membership, `equipment.view`, and tenant/building scope enforced by Laravel. `viewer`, `operator`, `admin`, and `owner` receive this permission in the current role seed. UUID route parameters are constrained server-side. Equipment read routes have `throttle:120,1`.

| Operation | Path and parameters | Success |
| --- | --- | --- |
| List | `GET /api/v1/organizations/{organization}/buildings/{building}/equipment` | `200 {"data":[Equipment,...],"meta":{"current_page":1,"per_page":25,"total":N,"last_page":N}}` |
| Detail | `GET /api/v1/organizations/{organization}/buildings/{building}/equipment/{equipment}` | `200 {"data":Equipment}` |

List query parameters: `page` (integer ≥1, default 1), `per_page` (1–100, default 25), `type_code` (active catalog code), `lifecycle_status` (one of six current values), `floor_id` and `zone_id` (UUIDs in the same building), and `q` (1–100 characters; case-insensitive code/name substring search). Filters combine with AND. When both location IDs are supplied, the zone must belong to the floor or Laravel returns 422. Results sort by `(code,id)`. The current GET API has **no direct-building-only or direct-floor-only filter**, no equipment type catalog GET, and no floor/zone labels in equipment JSON. The floor/zone equipment paths in OpenAPI are **POST creation paths**, not GET list paths; the mobile client must use the building list GET with filters. Detail is always under the building GET path.

The `Equipment` response has required keys `id`, `organization_id`, `building_id`, nullable `floor_id` and `zone_id`, `code`, `name`, nullable `description`, `type_code`, nullable `manufacturer`, `model`, `serial_number`, `lifecycle_status`, nullable `installed_on`, `commissioned_on`, `specifications`, `spec_schema_version`, and `created_at`, `updated_at`. Nullable keys are present with JSON null. `installed_on` and `commissioned_on` are `YYYY-MM-DD`; timestamps are date-time strings. `code` is canonical uppercase, up to 64 characters. Current lifecycle codes are `planned`, `installed`, `commissioned`, `active`, `out_of_service`, `retired`. The current catalog codes are `ahu`, `fcu`, `vav`, `fan`, `chiller`, `boiler`, `heat_pump`, `circulation_pump`, `motorized_valve`, `electrical_meter`, `water_meter`, `temperature_sensor`, `pressure_transmitter`, `co2_sensor`, `ddc_controller`, `gateway`, `other`.

`specifications` is null or a JSON object, with `spec_schema_version` null or 1 respectively; an empty object is valid. Version 1 permits `design_airflow_m3_h` (>0, air family), `design_flow_m3_h` (>0, hydronic), `design_capacity_kw` (>0, thermal), and `rated_power_kw` (≥0, air/thermal/hydronic/controls hardware), each ≤1,000,000,000. Metering, instrumentation and general families permit no keys. The backend limits serialized specifications to 4096 bytes. The response does not contain family, so the mobile UI must not infer family from raw field presence or promise family validation from list JSON alone. Show known keys with units `m³/h` or `kW` and a localized label; do not render arbitrary unknown keys as engineering quantities.

Contracted failures: 401 missing/invalid bearer or inactive account; 403 active member without `equipment.view`; 404 inaccessible/absent organization, building or equipment; 422 invalid list filter/pagination; 429 throttled. Transport failures and 5xx also need safe handling. Laravel alone authorizes and scopes data; Flutter response checks are an additional display safeguard.

## 3. Typed, null-safe Flutter model proposal

Create `features/equipment/equipment_models.dart` with immutable `EquipmentRecord`, `EquipmentSpecifications`, `EquipmentPageMeta`, `EquipmentListResponse`, and `EquipmentDetailResponse`. Keep `typeCode` and `lifecycleStatus` as validated nonempty strings rather than closed Dart enums: map known values to English/French display labels and show an escaped/raw code or localized “Unknown type/status” for future values. Preserve the raw code for diagnostics and filtering, without throwing away the rest of a valid record. Do not silently turn an unknown value into a known one.

`EquipmentRecord` fields mirror the response exactly, with nullable Dart fields only for the nullable JSON fields. Require canonical UUID shape for all IDs; require `zoneId == null || floorId != null`; require nonempty bounded code/name; parse date-only fields without UTC day shift and parse timestamps as instants. Reject malformed required fields or wrong JSON types with a safe invalid-response failure. Validate each record's organization/building against the request and detail `id` against the route. For a floor list require each row's `floor_id` to equal the floor filter; for a zone list require both returned floor and zone IDs to equal the route. Do not accept a record from another scope because its display name happens to match.

`EquipmentSpecifications` holds `schemaVersion` and typed optional numeric version-1 values. Require version/null consistency, numeric finite bounds, and known keys for version 1. If a future schema version appears, keep the equipment record displayable but mark specifications unsupported and show a localized unavailable message, never guess a unit or display raw arbitrary JSON. A future version requires a contract update before its fields are shown. `EquipmentPageMeta` parses the four integer metadata keys and applies `HierarchyPage`-equivalent checks: current page matches request, page size within 1–100, `last_page == max(1, ceil(total/per_page))`, page length plausible, and no duplicate IDs within/across pages. `EquipmentListResponse` owns the immutable records and meta; `EquipmentDetailResponse` owns one record. Use existing hierarchy parsing helpers where appropriate without changing their floor/zone contract.

## 4. Navigation and read-only screens

Proposed guarded Flutter routes (these are client routes, **not** new API paths):

| Entry | Flutter route | Server request | Meaning shown to user |
| --- | --- | --- | --- |
| Organization → Building Details | `/buildings/:building/equipment` | Building list GET, no location filter | **All equipment in this building**, including directly assigned building items and every floor/zone. `AHU-01` appears here. |
| Building → Floor Details | `/buildings/:building/floors/:floor/equipment` | Building list GET with `floor_id=:floor` | **Equipment on this floor and in its zones**. The API cannot isolate directly assigned floor items. |
| Building → Floor → Zone Details | `/buildings/:building/floors/:floor/zones/:zone/equipment` | Building list GET with both `floor_id=:floor`, `zone_id=:zone` | **Equipment in this zone**, directly assigned to the zone. |
| Any equipment list | `/buildings/:building/equipment/:equipment` | Building detail GET | One equipment item; push onto the list route so Back returns to its prior filter/page context. |

The `/equipment` drawer section needs an organization-scoped building chooser using the existing Buildings flow, then links to the building equipment list. It has no implicit “all organizations” inventory. Add a Browse Equipment action on Building, Floor and Zone detail screens, while retaining Floors and Zones actions. Explicitly allow only the new route shapes in the GoRouter guard; validate UUIDs before client requests and route to a safe unavailable state for malformed IDs. A direct detail link after authentication/organization selection must fetch its own record; it cannot rely on a prior list cache.

The list screen uses code/tag as the primary label and name as secondary, plus localized type and lifecycle status, scope heading, and location context. “Building level” means both IDs null; “Floor” means floor set and zone null; “Zone” means both set. Resolve parent names only from a matching organization/building floor/zone state already held in memory; otherwise show the returned IDs. Avoid N+1 requests and never infer a parent label from a different scope. Include initial loading, empty, offline/network, 403/404 unavailable, other error with retry, pull-to-refresh, and page loading/retry. Search, type and status filters may follow the base list in the same implementation stage; changing any filter starts at page 1 and cancels prior requests. The filter UI must not offer an unsupported “direct assignment only” toggle.

The detail screen displays tag, name, description if present, type, lifecycle, manufacturer/model and serial number if present, building/floor/zone identity or safe cached labels, installation and commissioning dates, and only known version-1 engineering quantities with units. Missing optional data shows a localized absent-value treatment. It has no edit, create, retire, delete, command, or hardware action. Both screens use `AppStrings` for English/French text, current theme colors and Material components; verify dark mode rather than hardcoding colors. Never render mock telemetry as live equipment data.

## 5. Data flow, failure policy and security

Use `EquipmentApiClient` over `protectedDioProvider` for the two GETs only, `EquipmentRepository` with `safeHierarchyRead`-style error mapping, and an `EquipmentController` with an explicit immutable `EquipmentScope(buildingId, floorId?, zoneId?, typeCode?, lifecycleStatus?, query?)`. The scope enforces zone→floor, carries list filters, and is part of state identity. Keep list and detail request identity separately so opening detail does not corrupt the list. On first page, refresh, filter change, pagination, route disposal, organization switch or logout, cancel superseded Dio requests. Before each state write check `ref.mounted`, captured organization context/generation, request serial, and exact active scope or detail ID. On return from a stacked route, reload if the current provider scope changed; do not show another building's cached results. Preserve existing pages on a page-two failure and offer retry; never append overlapping IDs. Do not persist inventory, specifications, or search terms to secure storage or disk.

Handle 401 through existing session invalidation/logout and guarded navigation. For 403/404 clear inappropriate displayed records and show “unavailable or no access” without exposing whether another tenant's ID exists; do not assume a permission denial alone means the selected organization membership vanished. Treat 422 as invalid request/filter state and show a safe error (rechecking URL scope/filters), 429 as rate limited with manual retry after an appropriate delay/`Retry-After` if present, and 5xx/timeouts/offline as retryable. Do not spin automatic retries or log tokens, headers, serial numbers, complete payloads or raw server error bodies. Respect the backend as the sole authorization authority. No mobile equipment write endpoint or edge/hardware command is proposed.

## 6. Verification plan for the later implementation

1. Model/contract tests: all required and nullable fields; building/floor/zone ancestry; malformed UUID and wrong detail ID; date-only values and timestamps; null/empty/known/unsupported specifications; bounds and units; all known and unknown future type/status values. Assert that a building-level `AHU-01` is included in an unfiltered building list and excluded from floor/zone lists.
2. API/repository tests: exact GET paths and query parameters for three scopes; bearer interceptor behavior; no POST/PATCH/DELETE; list metadata, duplicate IDs, stable page append, filter reset, 422 filter ancestry, 401/403/404/429/5xx and offline mapping.
3. Controller tests: initial/refresh/load more/retry; page-two failure retaining earlier records; request cancellation; late responses after route change, logout, organization switch and provider disposal; same building with two different floor/zone filters; stacked-route return reload.
4. Widget/router tests: building/floor/zone entry labels, detail/back navigation, deep links behind auth/organization guards, building-level visibility, empty/error/offline views, missing optional fields, English/French labels, dark theme, and no write controls. Reuse the existing building/hierarchy test patterns and add focused tests for the scope differences.
5. Runtime: on a local Android emulator and local backend, verify authenticated building list includes demonstration `AHU-01`, detail shows `retired` and building-level location, floor/zone lists apply their filters, refresh/pagination/offline recovery, Back/deep-link guard, English/French and dark mode, logout and reopen. Run `flutter analyze`, `flutter test`, and a debug APK build. iOS requires macOS/Xcode, simulator or device, matching authenticated flow, networking, secure-storage and navigation checks. Existing release storage, two-organization switching and release-mode performance gates remain separately open until observed.

## 7. Proposed implementation sequence and decisions for approval

1. Add contract parsing tests, model and GET-only client/repository, including scope and pagination validation.
2. Add controller tests and Riverpod state with cancellation, generation checks, page handling and failure policy.
3. Add localized list/detail widgets, optional search/type/status filters, and route/entry actions; preserve Floors/Zones navigation.
4. Add router/widget coverage, run Flutter checks, then validate Android against local data and iOS when a macOS runner is available. Update progress and runtime evidence separately. No equipment writes or gateway controls are part of this sequence.

Approval choices still open: (a) accept the proposed floor scope including descendant zones, or request a backend `zone_id IS NULL`/direct-only filter in a separate backend stage; (b) decide whether the drawer's Equipment entry should open a dedicated building chooser or reuse the existing Buildings list with an equipment intent; (c) decide whether search/type/status controls ship with the first read-only screen or a follow-up. The API supplies no catalog GET or location labels, so dynamic type names and complete parent-name resolution need separate contracts if required. The current proposal can proceed with local known-code translations and safe ID fallbacks after these product choices are resolved.
