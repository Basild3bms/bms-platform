# Database design

## M1 relational schema

| Table | Key fields and constraints | Purpose |
|---|---|---|
| organizations | UUID PK, unique slug, timezone | Tenant root. |
| buildings | UUID PK, organization FK, unique organization/code, timezone | Physical site. |
| devices | UUID PK, organization and building FKs, unique building/protocol/external ID | Equipment identity. |
| device_points | UUID PK, device FK, unique device/external ID, writable default false | Normalized point metadata. |

Laravel's starter user, cache and jobs migrations remain in place. User membership and tenant authorization are later work; no tenant data endpoint is exposed in M1. UUIDs are generated by application code, not by a database extension. PostgreSQL is the deployment database; SQLite in-memory runs the isolated M1 schema tests.

## Planned additions

M2.1 adds `personal_access_tokens`, `roles`, `permissions`, `role_permissions`, `organization_memberships`, `organization_invitations`, and append-only `audit_events`. It adds `users.is_active` with a true default so existing M1 users remain enabled during an additive migration. Memberships are unique by organization and user; a revoked membership remains inactive for audit history. Invitations store a hash of the one-time token and an expiration, never the token itself. Audit foreign keys restrict user or organization deletion when events reference them; PostgreSQL and SQLite triggers reject audit update and delete. PostgreSQL adds a composite building ID/organization foreign key on devices, while SQLite uses equivalent insert/update triggers, including a building tenant-change guard. The migration checks for existing mismatches and stops for repair if any exist. The seeded roles are viewer, operator, admin, and owner. Admin and owner can view and manage users; only a member with a higher rank can grant or change a target role. No database user or default credential is seeded.

M2.2C Stage 1 adds `floors` and `zones` under buildings. Both use UUID primary keys, explicit organization/building scope, timezone-aware timestamps, and restrictive parent foreign keys. Floors add signed integer `level` and unique `(building_id, code)`; zones add `floor_id`, `zone_type`, and unique `(floor_id, code)`. PostgreSQL composite foreign keys enforce floor/building/organization and zone/floor/building/organization consistency; SQLite insert guards provide equivalent parent checks. Both drivers block floor and zone reparenting, and SQLite blocks organization changes to a building with floors. Application validation plus unique indexes handle duplicate codes, including races. The migration creates no rows in the normal development database unless explicitly applied; rollback drops the new hierarchy and therefore requires a data-retention review if those tables contain records.

The local Docker PostgreSQL development database was later migrated for M2.2C and populated through authenticated HTTP only, with 3 floors and 6 zones under the existing demonstration building. Read-only checks confirmed 11 applied migrations, 12 new permission assignments, and matching organization-scoped audit references. Hardening changed only route validation and error handling; previously applied migrations and demonstration records were not changed during that review.

Rooms may extend the building hierarchy later. Telemetry samples carry point ID, source timestamp, ingest timestamp, value, unit, quality and sequence; partition by time and retention policy. Alarm, command, automation, energy and maintenance tables each carry organization and immutable actor context. Future device CRUD must also check building and device organization IDs in application authorization; no device write API exists in M2.1. Index tenant, point and time filters; test retention and restore procedures.
